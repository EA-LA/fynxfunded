# FYNX Trade engine and account email update — 20 October 2026

This release strengthens the isolated trading engine and prepares an independently deployable account-email update. **It is not deployed. Public checkout and trading remain paused.** The previously deployed account portal and account-ready emails remain the production baseline.

## Implemented

| Area | Result | Environment |
| --- | --- | --- |
| Account activation | A simulated purchase creates one $25K Phase 1 account. Orders are rejected until activation; concurrent activation emits one confirmation. | Local demo |
| Trade protection | Customers can edit or remove SL/TP on open positions. The server checks tick sizes and executable bid/ask, including profitable stops. | Local demo, web/iOS |
| Automatic execution | Stop fills, pending fills, and loss-limit shutdown commit even when the customer command is rejected. Durable rejection receipts prevent a retried command from executing again. | Local demo |
| Gaps | A pending order that fills beyond its protection closes in the same update. | Local demo |
| Progression | Passing Phase 1 creates an unactivated Phase 2 account and notification. Failure closes positions, cancels pending orders and retains history. Phase 2 completion requires review, with no payout automatically granted. | Local demo |
| Lifecycle messages | Account ready, activated, Phase 2 ready, failure, and review-required messages have branded HTML/plain text, account links, and idempotent local-mailbox delivery. | **Local mailbox only** |
| Purchased-account email | First activation queues a confirmation without enabling execution or starting a trading day. Current payment, account, owner and verified-email checks apply at send time. | Implemented, not deployed |
| Delivery status | Signed Mailgun events distinguish provider acceptance, delivery, delay, bounce and complaint. Customer views receive only an allowlisted status. | Implemented, not configured/deployed |
| Suppression | Bounces and complaints suppress later account mail until support review. Unknown send outcomes are held instead of automatically duplicated. | Implemented, not deployed |
| iOS parity | Matching activation, SL/TP editing, lifecycle inbox and purchased-account email status are implemented in the current local app and the native review branch. | Native verification tracked separately |

All execution prices are generated locally. Existing hosted TradingView charts are display-only and are not an execution feed. Development rules remain explicitly labeled: 8%/5% targets, 5% daily loss, 10% maximum loss, one trading day, three synthetic markets, one adverse slippage tick, and $3.50 commission per lot per side. These rules do **not** replace purchased rule snapshots or authorize production trading.

## Account-email deployment preparation

The owner has not approved this release yet. Prepare it with:

```sh
node scripts/prepare-trade-email-release.cjs
```

The output names a temporary release directory containing `release.json`, compiled functions and a command to use **after approval**. The only function exports are:

- `fundedTradeAccess`
- `sendTradeAccessEmail`
- `retryTradeAccessEmails`
- `tradeMailDeliveryWebhook`

The deployment leaves payment endpoints, stored financial records, checkout flags and the development engine unchanged. Web hosting and an iOS build are separate releases. Do not use the older seven-function deployment script to deploy this new webhook.

Before the approved deployment, securely configure `MAILGUN_WEBHOOK_SIGNING_KEY` in Firebase Secret Manager. This is Mailgun's **HTTP webhook signing key**, not the existing sending API key. Do not paste either key in chat or commit it. The sender still uses `MAILGUN_API_KEY`.

After deployment, configure the `mail.fynxfunded.com` delivered, temporary-failure, permanent-failure and complaint events to the actual HTTPS URL returned for `tradeMailDeliveryWebhook`. Keep unrelated webhook destinations. Verify the domain and a correlated account-mail delivery with one owner-authorized test before claiming production delivery tracking.

The implementation follows Mailgun's [signature verification](https://documentation.mailgun.com/docs/mailgun/user-manual/webhooks/securing-webhooks) and [event payloads](https://documentation.mailgun.com/docs/mailgun/user-manual/webhooks/webhook-payloads). It checks signature time, domain, job ID, recipient hash and provider message ID; stores receipt/token hashes; and does not persist raw payloads or recipient addresses. It requires unredacted `recipient` for correlation. If provider PII redaction is enabled, delivery tracking needs a reviewed alternative before launch.

The 24-hour signature window permits delayed provider retries. Duplicate events are acknowledged. Invalid signatures/events receive 406; a missing or mismatched job correlation receives 503 for bounded provider retry. Provider-accepted historical jobs without the new recipient hash stay unconfirmed; this release does not backfill them or resend them.

## Still required before customer trading

1. **Commercial execution-price rights and provider connection.** Free display widgets do not establish rights to use those prices for execution or distribute them as a customer feed. Owner must choose/approve a provider and licensed markets.
2. **Production execution services.** The loopback-only worker is a development harness. Production needs the approved feed adapter, durable position/order ledger, continuously monitored risk processing, recoverable jobs, scaling/load checks and operational controls before execution can open.
3. **Production evaluation policy.** Map immutable purchased rule snapshots to the production engine, including daily reset timezone, minimum days, instrument sessions, margin, spreads, fees, slippage, drawdown calculations and phase eligibility. Development constants are not a substitute.
4. **Stripe live configuration and controlled purchase/refund test.** Business approval was reported complete. Live keys, webhook configuration and an approved live test still require verification.
5. **Mailgun webhook configuration and delivery test.** Account-ready sending already exists; the new receipt/activation update needs its signing key, deployment approval and provider test.
6. **Native release.** Reconcile the older GitHub baseline with the current local app, finish simulator/device acceptance, sign/archive and approve TestFlight upload. The current app contains unrelated work that this PR does not claim to merge or release.
7. **Launch operations.** Final legal/operator documents, monitoring and incident handling, reconciliation/retention, refund/dispute controls, funding/payout review and an owner-approved release remain launch requirements.

No APNs work is needed for this update: the earlier notification test was confirmed by the owner as arriving and opening the inbox.
